# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository

`page-snapshot-extension/` is PageKeep (called Page Snapshot up to 1.1.1; the folder and the repository keep the old name), a plain-JavaScript Manifest V3 extension for Chromium browsers (Chrome, Opera, Edge…) that saves the active tab as an offline ZIP, or as a `.wsnp` file (Web SNaPshot, the project's own format, specified in `wsnp-format/FORMAT.md`; the popup's "Save as" choice, `settings.format`, `.zip` by default) (see its `README.md`). The viewer that will open `.wsnp` files is a separate repository, following `docs/VIEWER-GUIDELINES.md`; password protection belongs to the viewer, and the popup stays as simple as possible. It has no build step and no npm dependencies: load the folder unpacked on the browser's extensions page. It previously lived in `asantos43/projetos-ia-genericos` under `chrome-extensions/`, where a frozen copy remains; do not edit that copy.

Architecture: the toolbar button (or Alt+Shift+S) opens `popup.html`, the action popup under the icon: it opens idle, **Snapshot** starts a capture of the active tab (`popup-start`), **Cancel** stops a running one (`popup-cancel`, then the popup closes) or discards a finished one (`popup-reset`), and **Download** saves the finished ZIP (`popup-download`: `background.js` downloads the blob and waits for the file before clearing the capture); nothing is saved automatically, and a finished capture waits for Download or Cancel; the captured tab stays visible, so Chrome does not throttle its timers while carousels are stepped. `background.js` (a module service worker) keeps the capture ("job") in `chrome.storage.session`, sets the icon badge, and runs the capture in an offscreen document (`offscreen.html`), which lives on when the popup closes; the offscreen page only has `chrome.runtime`, so it asks `background.js` for every `chrome.tabs` / `scripting` / `debugger` call. One capture at a time. With the popup's "Load the whole page first" option (`settings.reveal` in `chrome.storage.local`, on by default), `inpage.js` first scrolls through the page and presses "Load more" buttons. With "Record what each choice shows" (`settings.choices`, **off** by default, because it acts on the live form), `inpage.js` chooses each option of every group of radio buttons, records the area that changes for each right after choosing it (ignoring what changes by itself, such as a countdown), then the questions that answer revealed (`parent`, inside its area, up to 4 levels and 40 groups), and puts the original choice back, reporting a group the site would not put back; the copy shows each area as it was before the capture (`original`). Offline, `lib/offline/choices.js` finds a question's area from its options (`up` levels above them) and brings in only what that question controls (what differs between its options' recordings, plus what the questions it revealed control), so every question keeps its own answer. Links to the page itself (`#fragment`, or a query parameter naming an element, such as `?jumpTo=bookmark:x`) become in-page links (`linksWithinPage` in `offscreen.js`), and `lib/offline/disclosure.js` opens the closed section a jump lands in. No host permissions: `activeTab` gives the captured tab, and files the tab had not loaded are downloaded by the tab itself through the debugger (`Network.loadNetworkResource`); see `docs/STORE-POLICY.md`, the Chrome Web Store checklist that every release must pass. `inpage.js` runs in the tab and snapshots the live DOM (and steps through carousels, and turns Monaco editors into plain text), with `inpage-main.js` reading editor text from the page's own JS world. `offscreen.js` (Cancel makes `background.js` tell `inpage.js` to stop and restore carousels, then close the offscreen document) reads the resources the tab already loaded through `chrome.debugger`, downloads the rest (throttled per host, retrying 429/503), rewrites URLs (the files go into `assets/images|styles|fonts|media|files/`, chosen by `assetFolder` in `lib/helpers.js`) and builds the ZIP with `lib/zip.js` (for a `.wsnp`: `mimetype` first, `manifest.json` with every file's type and SHA-256, the offline scripts in `_wsnp/offline.js` instead of inline, `_wsnp/preview.jpg`). The full help page is `help.html` (English) and `help.pt_BR.html`, linked from the popup's Help through the `help_page` message. Every text is in `_locales/en` and `_locales/pt_BR` (same keys); the offscreen page has no `chrome.i18n`, so it publishes texts as `{ key, args }` and `popup.js` translates them. `lib/helpers.js` holds the pure, Node-testable helpers. `lib/signing.js` signs a `.wsnp`'s manifest (wsnp-format/FORMAT.md section 12): one key pair per installation, Ed25519 or else ECDSA P-256, the private key a non-extractable CryptoKey in the extension's IndexedDB (never exported), the public key and fingerprint written into the file; `offscreen.js` signs the exact manifest bytes and adds `signature.json` right after `manifest.json` (format_version `1.1`), and on any failure writes the ordinary unsigned `1.0` file; `popup.js` shows the fingerprint in Help. `lib/offline/` is the offline library: one self-contained local script per kind of element (`disclosure.js`, `tabs.js`, `pager.js` for carousels recorded item by item, `slider.js` for carousels whose steps the capture recorded (strip place, part states, arrows, dots), `choices.js` for areas recorded per radio-button option, `splitter.js` for resizable panels (a handle between two flex panels, as react-resizable-panels builds them), `lightbox.js` for photo galleries whose large pictures the capture saved, `modal.js` for Bootstrap modals and dialogs, `toggles.js` for Bootstrap dropdowns, collapses and tabs, `editors.js`), listed with a `needed(html)` test in `index.js`; `offscreen.js` embeds only the modules a saved page needs.

The goal, in the user's words: the snapshot is a "photo" of the page to have offline, as close as possible to the online original: responsive, with all the content the page has (texts, images, files) and with its elements working (carousels, tabs…). Judge every change by how close the offline copy gets to the live page. The capture may act on the page to bring content in (scroll through it, press "Load more", step through carousels), always putting it back as it was.

Rules that shape the design:

- A snapshot must never contact the network when opened: the page's own scripts, `ping` attributes and cross-origin iframes are removed, and references to anything that could not be saved are dropped rather than left pointing online.
- The page's own scripts never go into the copy; the local scripts of `lib/offline/` are the extension's own, written only to reproduce the page's behaviour offline. Local scripts that restore page behaviour offline are welcome (add a module to `lib/offline/` when interactive content is already in the saved DOM, or when the capture can record what the page's script would do, as `slider.js` does); they must be self-contained and never use the network.

`PRIVACY.md` (English and Portuguese) is the privacy policy, published as the public gist https://gist.github.com/asantos43/a0566af48d0894dc44b72bee43b22da8 for the store; after changing it, run `gh gist edit a0566af48d0894dc44b72bee43b22da8 --filename PRIVACY.md PRIVACY.md` (confirm with the user first: it is an external action). `store/` holds the Chrome Web Store listing: `README.md` (field by field), `PUBLISHING.md` (the dashboard steps, in Portuguese), the descriptions (`description.en.txt`, `description.pt_BR.txt`, plain text, naming no other product) and the pictures. `docs/DEVELOPMENT.md` holds the background that is not in the code: tool versions, how to load and test in each browser, versioning and releases, and how this repository was extracted.

## Tests

`tests/` runs the extension in a real Chromium with Playwright (the only npm dependency; `npm install` there). Playwright's own Chromium, in `~/.cache/ms-playwright`, is required: the Flatpak Google Chrome/Edge are branded builds that ignore `--load-extension`, so they cannot load an unpacked extension under automation.

- `npm run smoke` (`node smoke.mjs [extension folder]`, default `../page-snapshot-extension`): the extension loads and each top-level `.html` page opens without an uncaught error.
- `npm run carousel` (`node carousel.mjs`): end-to-end capture of a local test page with a 12-item carousel and files from a second site the extension has no permission for, through the real popup (`chrome.action.openPopup`): all items recorded, the page put back on item 1, the popup's flow (opening starts nothing; idle / running / done buttons; nothing saved before Download; Download saves and resets; Cancel on a finished capture discards it), the ZIP's carousel working offline with no network request, closing the popup mid-capture, Cancel during a capture (popup closed, carousel restored, nothing saved, debugger released). Playwright cannot reach the real popup's page, so the tests open `popup.html` in its own window, taking the test page for the active tab (`tests/popup.mjs`), and click Snapshot there; `activeTab` cannot be granted under automation, so it loads a copy of the extension with the test site as a host permission.
- `npm run library` (`node library.mjs`): end-to-end test of the offline library on a local page imitating the most common elements (a Bootstrap-style carousel switching by class with indicators, a Swiper-style strip with bullets, a Fancybox-style gallery, a Bootstrap modal, a `<dialog>`, a dropdown, an accordion, tabs, links to places in the page itself written as its address), used offline after the capture.
- `npm run choices` (`node choices.mjs`): end-to-end test of the opt-in option "Record what each choice shows" on a local page whose script builds the next step only when a radio button is chosen (questions three levels deep), with a countdown ticking: off, no radio button is touched; on, every group recorded, including the revealed questions, the live page put back, a group that keeps the last option reported; offline, each option shows its content.
- `npm run store-policy` (`node store-policy.mjs`): static checks from `docs/STORE-POLICY.md`: the exact permission list (each justified there), no host permissions, no eval or remote code, no network host named in the code, the two locales complete and every message used, name/description within the store's limits in each language, the store pictures' sizes and descriptions, icons without third-party metadata.
- `npm run screenshots` (`node screenshots.mjs [--lang=en|pt-BR] [--out=<folder>]`): real screenshots of the popup (idle, running, done, failed file, Help open; every one shows the Save as choice, `.wsnp` selected in all but the failed one) and of the saved page opened offline (a `.wsnp` renamed to `.zip` and unzipped), from a local example news site reached as `http://harbortimes.example/` (a made-up news site, `tests/example-site.mjs`); by default both languages into `page-snapshot-extension/images/screenshots/<en|pt_BR>/`, used by `help.html` / `help.pt_BR.html` and the READMEs. Each shot is checked first (language, no untranslated key, the right moment of the capture) and the script exits 1 otherwise; a capture in progress is frozen in the popup at the checked moment, the saved `.wsnp` is validated and its signature checked against the key shown in the Help, and a second run changes no picture (fixed clock in the test copy, a still progress bar, a sample fingerprint in the Help shot). Rerun it when the popup's look or texts change, and look at the images before committing.
- `node readme-images.mjs [--url=…] [--lang=pt-BR]` (needs the internet): captures a real site (default https://www.tudogostoso.com.br/) and writes the popup and the saved copy opened offline to `docs/images/readme/`, for the main README only; fails if the copy tries to reach the network (it found the `compression-dictionary` bug). Pictures of third-party sites never go into `page-snapshot-extension/` or `store/`.
- `node store-images.mjs`: the Chrome Web Store pictures in `store/images/<en|pt_BR>/` (five 1280×800 screenshots, one per feature and the last one on `.zip` or `.wsnp`, the 440×280 small tile and the 1400×560 marquee), built from the extension's screenshots; run `npm run screenshots` first if the popup changed.
- `npm run wsnp` (`node wsnp.mjs`): the reference WSNP tools without a browser: `wsnp-check.mjs` (the validator, also a CLI: `node wsnp-check.mjs <file.wsnp> [--password=…]`) accepts a well-made file and refuses broken ones (including the signature checks of `wsnp-format/FORMAT.md` section 12 and its known-answer vector, run through `lib/signing.js` with both algorithms), and `wsnp-crypt.mjs` (password protection, for the viewer to reuse; not in the extension) round-trips and refuses wrong passwords and damaged chunks. The `.wsnp` the extension writes is checked in `carousel.mjs` (validated, served from the archive under a strict CSP, renamed to `.zip`).
- `npm run publish-script` (`node publish-script.mjs`): runs the store upload script against a fake Chrome Web Store on 127.0.0.1 with a throw-away key: no secrets (notice, exit 0), a normal upload (signed token, exact zip, status, publish), a rejected package, a wrong key.
- The rest of the capture logic was verified with throw-away jsdom harnesses that are not in the repo.


**The format's description is in its own repository.** `FORMAT.md` and `MANIFEST-SIGNING.md` live in `wsnp-format` (`~/Dev/AI/projetos/github/wsnp-format`, https://github.com/asantos43/wsnp-format), shared with the viewer (`wsnp-viewer`); PageKeep keeps no copy. A format change is made there first, then PageKeep follows. Comments and docs here cite it as `FORMAT.md section N`. In the other direction, `tests/wsnp-check.mjs`, `wsnp-crypt.mjs`, `wsnp.mjs` and `lib/zip.js` are the reference tools of which the viewer keeps copies: after changing one, say so in the pull request so the viewer's copies are refreshed. (`docs/VIEWER-GUIDELINES.md` is an older, separate document.)

When behaviour changes, update `page-snapshot-extension/README.md` and add a line under `## [Unreleased]` in `CHANGELOG.md`.

`.claude/settings.json` pre-approves `npm install`, the smoke test, `node --check` and read-only git commands.

## Releases

`.github/workflows/release.yml` publishes a release each time a pull request is merged into `main` (and on demand via `workflow_dispatch`): it releases the manifest version if it has no tag yet, otherwise raises the last number (1.0.0 → 1.0.1) and commits "Version x.y.z" to `main`, runs the smoke, carousel, library, choices, store-policy, publish-script and wsnp tests, zips the extension (plus `CHANGELOG.md`) as `pagekeep-<version>.zip` and publishes `v<version>`. Releases go to the Chrome Web Store **only when the user asks**: a pull request labelled `store` (or a manual run with the `store` option) also sends the same zip for review after the GitHub release; a release already published is sent with the `.github/workflows/store.yml` workflow ("Send to the Chrome Web Store", run by hand, version as input). Both use `.github/scripts/publish-to-chrome-web-store.sh` (API v2, service account; only with the `CWS_PUBLISHER_ID`, `CWS_ITEM_ID` and `CWS_SERVICE_ACCOUNT_KEY` secrets, which the user sets, and never for a pre-release). Never add the `store` label or run the store workflow unless the user asked for that release to go to the store. A pull request labelled `no-release` is merged without a release. For a minor or major release, raise `version` in `manifest.json` inside the pull request. Every pull request adds its user-facing changes as lines under `## [Unreleased]` in `CHANGELOG.md`; the release moves them into the version's section and uses that section as the release notes. After a merge, `git pull` picks up the bot's version commit. See `docs/DEVELOPMENT.md` → Versions and releases.

## Git policy

The remote is `origin` = https://github.com/asantos43/webpage-snapshot (private; keep it private). The default branch is `main`. Never commit or push directly to `main`: make every change on its own branch created from an up-to-date `main`, push the branch and open a pull request (`gh pr create`); the user reviews it and decides when to merge. The only commits that land on `main` by themselves are the release workflow's "Version x.y.z" bumps.
